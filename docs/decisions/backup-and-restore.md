### Phase: Implementation

**The acceptance test found an eleventh widening point nobody designed** — A13 identified ten places a system_check alert is rejected. Driving the real emission path end to end found `_event_from_row`, which carries its own closed set of source kinds. Like the other ten it fails SILENTLY — process_pending_event catches the ValueError, writes classification_status='rejected', enqueues no delivery, logs no failure, and the worker's orphan cleanup later DELETEs the row. Without the acceptance test the alert saying backups were dead would itself have been silently dropped. This is A13's lesson landing a fourth time.

## 2026-08-21 — 2026-08-27-add-gx10-backup-scheme

### Phase: Implementation

**Two bugs were caught by tests rather than by reading** — `int(hours or 48)` in the check-window calculation: zero is falsy, so a misconfigured backup_staleness_hours=0 silently became 48 hours and defeated the floor meant to clamp it. And the executor's live run showed the digest measures the CIPHERTEXT, not the source — correct and load-bearing, since the size read-back compares against the stored object, but easy to 'fix' backwards. Both are now pinned by tests.

## 2026-08-21 — 2026-08-27-add-gx10-backup-scheme

### Phase: Plan

**Freshness derives from a bucket-side manifest, not cron.job_run_details** — The question that matters is whether an artifact arrived at the destination, not whether the source believes it ran. A manifest answers that, is provider-independent, and survives destruction of the source host.

## 2026-08-21 — 2026-08-27-add-gx10-backup-scheme

### Phase: Implementation

**Retention is a dry-run-by-default renderer that cannot delete** — The applier sets provider-side expiry policy and issues no delete call, asserted by a test. Provider-side expiry keeps working while gx-10 is down, and an unattended process with delete rights over the backup target is the single most dangerous component such a system can have — a bug in it destroys the backups instead of the data.
