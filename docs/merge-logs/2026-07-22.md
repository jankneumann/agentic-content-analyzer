### PR #463 — P2 from `chatgpt-codex-connector` (fixed, not deferred)

`src/services/batch/workers.py:213` — permanent submission failures were requeued forever.
`run_batch_submit` returned every failed claim to `pending`, including deterministic
rejections, so the next maintenance tick reclaimed the identical rows and created another
failed `batch_jobs` row without bound.

Fixed in `a780e1e7`. `_is_permanent_submission_error` classifies `ValueError` — which
`submit_batch` documents as its deterministic rejection (oversized inline payload, empty or
duplicate request key, non-`google_ai` model) — and routes those requests to `FALLBACK`
instead. That is the same terminal handling the poll sweep already applied to failed and
expired jobs, and `run_sync_fallback` bounds it via `fallback_attempts` with a terminal
`FAILED` on exhaustion, so the queue drains *and* the work still completes. Transport and
credential errors keep the existing requeue behaviour.

Chose `FALLBACK` over `FAILED` deliberately: marking rows failed would have satisfied the
review comment while silently dropping user work.

Two regression tests added, **both verified to fail against the pre-fix behaviour** by
temporarily stubbing the predicate to `return False`:
- `test_permanent_failure_routes_requests_to_fallback`
- `test_permanent_failure_does_not_respawn_jobs_each_sweep` (two sweeps, one failed job)

### What the skipped CI was hiding: an import-order test failure on #463

The first real CI run on #463 (only possible once its base became `main`) failed
`test (services-stack)` — a **required** check —
on `tests/test_services/test_llm_router.py::TestGenerateSyncGeminiProvider::test_gemini_sync_creates_client_and_calls_api`,
with `FileNotFoundError` from `ssl.py: context.load_verify_locations(...)`. Reproduced
locally byte-identically (1 failed, 262 passed); the same shard passes on `main`.

Root cause is import-order fragility, not a router regression:

- `_generate_gemini_sync` does `from google import genai`. That resolves via
  `getattr(google, "genai")` once the submodule has been imported anywhere in the process.
- The old test injected a fake module into `sys.modules["google.genai"]`. Once the parent
  package has the attribute cached, `sys.modules` is never consulted — so a **real** client
  was constructed and attempted a live TLS handshake.
- #463's new `test_batch_disabled_regression.py` patches `"google.genai.Client"` by string.
  Patching by string *imports* the submodule, binding it on the parent package. That is the
  more robust style, but it made the older test's latent assumption fail.

So the old test only ever passed by accident, for as long as nothing earlier in the shard
imported `google.genai`. Bisected to the exact file by running each new batch test file
paired with the failing test.

Fixed in `993e679c` by patching `google.genai.Client` directly. A second, subtler problem
surfaced while fixing it: the test also did
`patch("src.services.llm_router.os.environ.get", return_value="fake-api-key")`, which is
**process-wide** — imports triggered inside the block (`google.genai` pulls in `websockets`,
which reads int-valued settings) received the string too and raised
`ValueError: invalid literal for int()`. Replaced with `patch.dict(os.environ, ...)` scoped
to `GOOGLE_API_KEY`. Verified in three orders: isolated, immediately after the batch
regression file, and across the full shard (1435 passed).

This is the single strongest argument in this session against merging a stacked PR on the
strength of a `CLEAN` merge status. The defect was present from the moment #463 was opened
and no check would ever have reported it while the base was not `main`.

### Unrelated finding: environment-dependent test on main

`tests/cli/test_curate_commands.py::TestCurateYoutubeRss::test_apply_disables_dead_channel`
passes on main and in CI, but fails on any machine where a YouTube API key resolves.

`curate youtube-rss` picks its transport from ambient config:

```python
if via_api is None:
    via_api = use_oauth or bool(get_settings().get_youtube_api_key())
```

The test mocks only `check_rss_feeds`. With a key present it takes the unmocked
`check_youtube_feeds_via_api` path, really calls the API, both fabricated channels fail, and
the *live* channel is disabled too — which is exactly the assertion that trips.

Confirmed by resolving the key in both worktrees: `True` in the batch worktree (which has an
`.env` symlink), `False` in the main worktree. Note that setting the `YOUTUBE_API_KEY`
environment variable to an empty string does **not** suppress it — `get_youtube_api_key()`
resolves through the profile/secrets layer, not that variable.

This is the CLAUDE.md "settings tests pick up .env" gotcha in a subtler form: the test's
outcome depends on which of two transports ambient config selects. Left unfixed — unrelated
to both PRs and out of scope for a merge session — but it is a real test-isolation bug.
