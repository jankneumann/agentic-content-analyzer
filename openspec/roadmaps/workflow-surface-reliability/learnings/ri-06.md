  outcome: 'A report cannot establish its own completeness - nothing inside it says

- title: Coverage is checked against the selection, not the descriptor; the planned
    rule was wrong
  outcome: 'D7 named the rule ''fail when any descriptor-declared interface is unevaluated''.

    against descriptor.all_interfaces(), so `--categories validation --offline` evaluates
    2 scenarios, passes 100%, and reports 29 of 31 interfaces unevaluated - correctly.

    checks fill the gap that scoping opens: every interface in per_interface must
    be descriptor-declared or in a reviewed exception set (a mistyped step command

  - Drop the coverage check entirely and rely on the scenario-count check - misses
    the typo case, where the count is right and the coverage is not
  - Widen the descriptor per run so its denominator equals the selection - changes

- title: The mutating scenarios must not depend on whether the target drains its own
    queue
  outcome: 'The first real run of the operation-control scenario failed, and the diagnosis
    was worth more than the fix. src/api/app.py starts an embedded queue worker when
    worker_enabled is set, so a plain uvicorn target processes its own operations
    - and neither /health nor `capabilities` reports whether it does. A submitted
    operation therefore reaches a terminal state on its own on one target and sits
    queued indefinitely on another, from an identical sequence of steps, and the gate
    cannot classify the difference the way it classifies the runner and the target.
    Every step is now written to hold under both, and verified that way: the whole
    mutating suite passes against a local backend with the worker enabled and again
    with it disabled. The cost is named rather than hidden - `cancel` asserts only
    that it returned a parseable document, because its exit code is 0 from a queued
    operation and 1 from an already-failed one, and `retry`''s success path is uncovered
    because retry requeues from `failed` only.'
  alternatives_rejected:
  - 'Design for a drained queue - it is the default and the realistic staging shape,

  - Tag the scenarios `requires-idle-queue` and refuse when it does not hold - there

  - Assert a loose expectation that both outcomes satisfy - `expect` has no one-of

- title: A selection that cannot fit the runner is refused before the run, not diagnosed
    after it
  outcome: 'Phase 4 already detects silent truncation, but only from a report - which
    for a mutating run means after an arbitrary subset of the durable work has been
    submitted. The tier arithmetic is computable from the selection alone, so the
    gate now runs it up front and refuses with the same exit code, before materializing
    anything. Same verdict, nothing written when it is reached. This is also what
    keeps the two dispatches honestly separate rather than by habit: read-only fits
    at 16 scenarios and mutating at 10, and together they exceed the critical tier
    by exactly one. Demonstrated: a combined --categories run exits 5 naming the overflow.
    A test pins all three numbers, so if UP-6 lands and a merged run becomes possible,
    the test says so.'
  alternatives_rejected:
  - Rely on the Phase 4 report check alone - correct verdict, arrives after the submissions
    it should have prevented
  - Batch the mutating scenarios so a combined run fits - buys one slot at the cost
    of masking (a failing operation type would hide the rest of its batch), to enable
    a run that is not a supported mode
  - Lower the mutating scenarios' priority so they land in the remainder tier - they
    are the most important scenarios in the suite; putting them where truncation reaches
    first inverts the whole tier design
- title: '`{{ name }}` is two mechanisms sharing one delimiter, and which applies
    depends on another field'
  outcome: The suite accounting rejected the operation-control scenarios outright,
    reporting `references undeclared parameter 'operation_id'`. It was half right.
    The pinned generator renders a template through Jinja2 with StrictUndefined only
    when it declares a `parameters` block; without one, `_expand_parameters` returns
    the template untouched and the braces survive to the evaluator, which interpolates
    them at runtime from values earlier steps captured. So the same syntax means a
    generation-time parameter or a run-time capture reference, and the two are mutually
    exclusive - a parameterized template cannot capture, because generation consumes
    the braces before the evaluator sees them. The accounting now checks both readings
    plus capture ordering, which is what lets any scenario chain steps at all.
  alternatives_rejected:
  - Use the CLI client's `[REDACTED:env_var]` substitution instead, which Jinja2 ignores
    - works only inside `args`, so assertions could not reference captured values,
    and it would encode a workaround for a rule we had misread
  - Relax the accounting to ignore every `{{ }}` it cannot resolve - restores the
    silent drop the check was written to prevent
  - Give the mutating scenarios a parameters block so the existing rule applies -
    would have destroyed the capture references at generation time and dropped every
    expansion with a log warning
- title: Pinning the runner's ref pinned one node of a graph; the gate now owns the
    whole closure in a lock it does not share with the application
  outcome: D2 acquired the runner with `uvx --from 'gen-eval @ git+...@<sha>'`, and
    for six phases that read as fully pinned - the ref is immutable and the vendored
    schemas were generated from it. It is not. `uvx` resolves the transitive dependencies
    fresh on every invocation, so the enforcing gate was reproducible in the runner
    and floating in everything the runner imports. Replaced with a repository-owned
    uv project at `evaluation/runner/` whose direct requirement is still the immutable
    SHA and whose complete runtime and build closure is checked in as `evaluation/runner/uv.lock`;
    the gate invokes it as `uv run --project ... --locked --exact --no-dev --no-python-downloads`,
    so lock drift is fatal rather than silently resolved. `package = false` and a
    separate project directory keep it a tool rather than an application dependency
    - the root pyproject.toml and uv.lock are untouched and the runner's transitive
    dependencies cannot collide with this project's.
  alternatives_rejected:
  - Keep uvx and accept floating transitive dependencies - the gate's whole claim
    is that its verdict is a property of the repository, and a verdict that changes
    when an unrelated upstream releases is not that
  - Add the runner to the root pyproject as a dev dependency - pins the closure but
    merges it with the application's, so a gen-eval transitive bound could constrain
    what the product itself can install
  - Vendor the runner source into the repository - pins everything and destroys the
    upstream relationship the contract split was designed around; the pin would stop
    being a pin and become a fork
- title: Once UP-1 through UP-4 landed, 'verified by construction' had to be deleted
    rather than kept as a fallback
  outcome: 'While `--print-contract-version` did not exist upstream, a pinned candidate
    was trusted by construction: it was installed from the exact ref the schemas were
    generated from, so the version was true by definition. The published console script
    now answers the probe, and the tempting move was to keep the construction argument
    as a fallback for when the probe fails. That is exactly backwards. If a pinned
    runner cannot complete the handshake, the thing that failed is the assumption
    the construction argument rests on, so the fallback would fire precisely when
    it is least entitled to. A pinned candidate that fails the probe is now MISMATCH
    - broken - and the failure detail carries the probe''s exit code and last output
    line instead of an empty string.'
  alternatives_rejected:
  - Keep construction as a fallback for probe failure - converts the one signal that
    the pin is not what it claims into a reason to trust it
  - Treat a failed probe on a pinned runner as `unverifiable` like an arbitrary override
    - unverifiable is tolerated locally, and a broken pin should not be tolerated
    anywhere
- title: Retaining evidence is publishing it, so the retained report is a minimized
    document that is re-validated after minimization
  outcome: 'A gen-eval report embeds what the CLI actually printed while talking to
    the target - stdout, stderr, and captured values from a real backend. Uploading
    that as a build artifact makes every one of those observations downloadable by
    anyone with access to the run, and the staging job runs against a deployed target
    with an admin key. `scripts/minimize_gen_eval_report.py` now writes a report without
    raw target observations and validates the *minimized* document against the report
    schema, not just the original: a redaction that produced a schema-invalid document
    would otherwise be discovered by whoever tried to consume the evidence. Both CI
    jobs upload only the minimized copy, and retention is conditional on that validation
    succeeding.'
  alternatives_rejected:
  - Upload the raw report and rely on repository access control - makes the blast
    radius of an access mistake the whole observation set, for a convenience nobody
    asked for
  - Skip retention entirely - the report is the only durable answer to 'what did the
    CLI actually do on that run', which is the question this roadmap item exists to
    make answerable
  - Minimize without re-validating - the minimizer is code, and code that silently
    produces an unparseable artifact is worse than no artifact
- title: The two CI jobs differ in trigger, target, and credential, so they are two
    jobs rather than one job with a matrix
  outcome: '`read-only` runs on every pull request against an ephemeral localhost
    backend it boots itself - Postgres service container, migrations, uvicorn with
    `WORKER_ENABLED=false` - and needs no secret beyond test values. `staging-mutation`
    runs only on `workflow_dispatch` from `main`, against the protected `release-smoke-staging`
    GitHub environment, and is the only job that sees a real `ADMIN_API_KEY`. The
    target policy is materialized in-job with `jq` from that environment''s `vars`,
    so no policy naming a real origin is ever committed and the deny registries come
    from the same environment that gates the credential. A matrix would have made
    the mutating job''s approval gate an expression rather than a structural property.'
  alternatives_rejected:
  - One job with a matrix over categories - the mutating leg's protection is the environment
    binding, and a matrix leg cannot be bound to a different environment than its
    siblings
  - Run mutations on pull requests against the ephemeral backend - the policy model
    requires HTTPS for every non-local class, so there is no localhost path, and inventing
    one would mean a second opinion about the safe set
  - Commit a staging policy file - puts a real origin and its deny registries in the
    repository, where they drift silently and are readable by anyone
- title: Report credibility is validated at threshold zero so a failing run still
    leaves evidence, without letting that validation pass the gate
  outcome: 'The retention step re-runs the report validator with `--fail-threshold
    0`. That still checks schema, expectation completeness, numeric bounds, and grouping
    - everything that makes a report worth keeping - while declining to re-assert
    the 95% pass rate. The run step already asserted that, under `continue-on-error:
    true`, and a final enforcement step requires both outcomes. The result is that
    the most useful artifact, the report from a failing run, is the one that survives;
    folding the threshold back into the retention step would have thrown that away
    exactly when it was needed.'
  alternatives_rejected:
  - Validate at the real threshold in the retention step - drops the evidence for
    every failing run, which is every run anyone actually needs it for
  - Retain unconditionally without validating - keeps unparseable or incomplete reports
    and makes the artifact's presence meaningless as a signal
  - Let the retention step's success stand in for the gate - a credible report of
    a failing suite would then turn the job green

## Decisions
- **Split the evaluation contract from the evaluation runner**: The contract (descriptor, scenario, and report schemas, thresholds, validator) lives in ACA, pins a gen-eval contract version, and needs no gen-eval install. The runner is a pinned versioned artifact. Cross-repo consistency is a contract problem, not a runtime problem - trying to solve it by sharing a runtime is what kept producing a path dependency.
- **Acquire the runner as a pinned artifact via uv tool, not a sibling path**: Verified working today: uv tool install 'gen-eval @ git+https://github.com/jankneumann/agentic-coding-tools.git@<sha>#subdirectory=packages/gen-eval' installs the executable into an isolated env, leaving pyproject.toml and uv.lock untouched. Pinned, reproducible, and installable in a cloud sandbox, VM, Docker build, or CI. Migrating to artifactory.rotkohl.ai later is a lock-file URL change, not a redesign.
  - Rejected: Sibling-checkout thin runner - superseded; see the deviation below
  - Rejected: Central shared eval service - cannot drive a CLI transport at all, since gen-eval spawns the command under test with create_subprocess_exec
  - Rejected: Container image runner - mirror problem: gen-eval in a container cannot spawn the host's aca; containerizing both is a heavier, different gate
  - Rejected: Standalone compiled (Rust/PyInstaller) runner - attractive end-state, poor next step: gen-eval is Python with optional mcp/sdk/db extras, so bundling means a platform matrix and dynamic-import fragility
- **No skip semantics in any enforcing context**: available / absent / broken. broken is fatal everywhere; absent is fatal under enforcement and cannot occur in CI because CI installs the pin. The contract layer runs and enforces regardless of runner state, so an unreachable runner never silently reduces coverage.
- **Single-source the production mutation guard on ri-04's target policy**: Mutating categories consume src/release_smoke/models.py TargetClass plus the production_target_ids / production_origins deny registries and their validators. One place enforces 'production is not a mutation target'.
- **Read coverage from the report; validate before trusting the threshold**: gen-eval's GenEvalReport already emits per_category, per_interface, and unevaluated_interfaces, so the validator asserts unevaluated_interfaces is empty rather than recomputing coverage. Minimum total and per-category counts guard the zero-scenario vacuous pass that --fail-threshold alone admits.
- **The gate owns scenario selection, because the runner's --categories flag is inert**: Verified rather than assumed: `--categories discovery` against the checked-in suite evaluated all 16 scenarios across all three categories. In gen-eval at ref 600744a5, args.categories reaches GenEvalConfig and is never read again; the only path into the generator's filter is feedback.suggested_focus, which is None on iteration 1, and max_iterations defaults to 1. So the filter is unreachable. This matters because selection is a SAFETY boundary in this design - mutating categories are held back by it - so had Phase 5's workflow-submission scenarios been authored assuming the flag works, every `make gen-eval` would have submitted durable work against whatever database was configured. src/cli_gen_eval/selection.py now resolves the selection, copies the chosen scenarios to a scratch dir, and synthesizes a per-run descriptor carrying the declared command list intact so the coverage denominator survives.

  - Rejected: Point scenario_dirs at the per-category subdirectories - insufficient, because --offline selects on a tag and validation/ is deliberately mixed (2 of its 4 scenarios need a backend)

  - Rejected: Probe via `aca capabilities` - puts a command under test inside the gate's own precondition check, so a 500 or a serialization regression would be reported as 'target unreachable' and refused rather than as the failing scenario it is
  - Rejected: Skip backend-dependent scenarios when nothing is listening - the exact defect this roadmap item exists to remove, one layer up

TemplateGenerator returns scenarios[:max_scenarios_per_iteration] (50, absent from its CLI); then Orchestrator._prioritize_scenarios buckets what survives and allocates int(50*0.40)=20 slots to --changed-features-ref matches, int(50*0.35)=17 to priority<=1, and the remaining 13 to everything else. Recorded in the pin under runner_limits, modelled in src/cli_gen_eval/suite.py, asserted in the drift test.

  - Rejected: Shard by category across invocations - insufficient, since plumbing alone is 32 and exceeds both tier caps
  - Rejected: Cover only 13 of 31 commands - abandons the coverage floor the sweep exists to be

None was needed - all 31 answer --help hermetically, verified by introspecting the Click tree rather than scraping Rich-wrapped help text, which produced phantom entries.   - Rejected: Compare only the total count, as the task specified - a shortfall then reports a number and sends you to the runner's logs to find out which work was lost
  - Rejected: Trust the runner's own exit code - it is computed from the reduced set, so it is structurally incapable of noticing the reduction

Measuring it showed it would reject every partial run: the runner computes coverage_pct against descriptor.all_interfaces(), so `--categories validation --offline` evaluates 2 scenarios, passes 100%, and reports 29 of 31 interfaces unevaluated - correctly. The check is now scoped to the interfaces the selection addresses. Two further checks fill the gap that scoping opens: every interface in per_interface must be descriptor-declared or in a reviewed exception set (a mistyped step command credits a phantom interface and leaves the real one uncovered, with no runner error), and each scenario's declared `interfaces` must match what its steps will credit. Coverage is read from the report's own fields rather than recomputed (D7's other half), because a second implementation of the runner's aggregation would disagree with it in ways indistinguishable from the defect it is meant to find.
  - Rejected: Keep the emptiness rule and only ever run the full suite - gives up category-scoped runs, which is what CI needs for a fast PR job
  - Rejected: Drop the coverage check entirely and rely on the scenario-count check - misses the typo case, where the count is right and the coverage is not
  - Rejected: Widen the descriptor per run so its denominator equals the selection - changes the coverage denominator itself, so a genuinely uncovered command would stop being visible as one
- **'The suite failed' and 'the report is not credible' get different exit codes**: Exit 1 stays 'a scenario failed', which is a defect in aca. Exit 5 is new: the run finished but its report cannot decide the question - scenarios dropped, coverage missing, counts that contradict each other, numbers out of range. The two land on different desks, and collapsing them would hide the second behind the first, which is precisely the failure mode this roadmap item exists to remove.   - Rejected: Report an incredible run as a suite failure (exit 1) - the reader concludes aca is broken and goes looking for a product bug that does not exist
  - Rejected: Report it as a usage error (exit 2) - nothing about the invocation was wrong
  - Rejected: Let the runner's --fail-threshold be the only gate - it computes the rate from whatever survived truncation, so 100% of a third of the suite passes it
- **Fixtures are recorded runner output; the negative cases are mutations in the test**: tests/fixtures/gen_eval/ holds two real runs - full and --offline - each paired with the expectation the gate wrote for it. Only edit is truncating captured stdout bodies over 120 chars, which removed about 120 KB of --help screens; a test asserts the fixtures are still schema-valid so the truncation cannot have corrupted them quietly. No malformed report is checked in: each is derived in the test by mutating a loaded fixture, so the mutation sits beside the assertion it trips and cannot drift from the fixture it came from. The validator itself was then mutation-tested - disabling each check fails only the tests naming it, including reverting the scoped-coverage rule to the naive emptiness rule, which fails exactly the test documenting why it is wrong.
  - Rejected: Hand-author the reports - a fixture that restates what we believe the runner emits proves the validator agrees with our belief, not with the runner
  - Rejected: Check in a report-truncated.json - it would assert that scenarios went missing; `report['verdicts'][:8]` in the test demonstrates it
  - Rejected: Keep the reports byte-complete at 167 KB - the trimmed content is help text no check reads, and it dominated the artifact
- **The guard binds the policy to the origin the CLI will dial, which is the check that makes the rest mean anything**: D6 single-sourced the classification on release-smoke's ProtectedTargetPolicy, and that held completely - the model already rejects a staging policy carrying a production identity, one resolving to a production origin, and one with empty deny registries. Verified each against the real model before writing a line of guard code, which is why the guard contains no deny-registry logic at all: `production_target_ids` appears nowhere in it. What D6 did not say is what the policy is a policy ABOUT. A document declaring target: staging describes some target, not necessarily the one the scenarios will submit to, so the guard resolves the CLI's own base URL from project settings - the same source target.py probes, for the same reason - and refuses a mismatch. Without that comparison the policy is correct, adjacent to the work, and attached to nothing.
  - Rejected: Trust the policy's self-description - accepts a correct staging policy while the scenarios submit somewhere else entirely, which is the exact accident the guard exists to prevent and the likeliest one (a correct policy file and an unchanged local profile)
  - Rejected: Probe the declared api_origin for liveness instead - proves the target exists, not that it is the one under test; reachability is a separate question already answered by exit 4
  - Rejected: Define a local target class so developers can run the mutating suite - the policy model requires HTTPS for every non-local class and release smoke excludes local from mutation, so this would have meant a second opinion about the safe set, which is precisely what D6 forbids
- **The guard runs before runner resolution, so a production attempt is never preempted by a broken runner**: Originally placed after runner resolution, where the gate's other category logic lives. Moved ahead of it. Both orderings are safe - nothing is submitted either way - but only one reports the true finding. An operator who points the mutating suite at production should be told that, not 'your runner is broken'. The move also makes 'no workflow was submitted' structural rather than a claim about control flow: the refusal is reached before a runner is looked for, before a selection is materialized, before any subprocess exists. The tests assert it by making both subprocess.run and resolve raise if reached, so a guard that decided correctly but late would fail.
  - Rejected: Keep it beside the other category handling - reads better as code and reports the wrong thing
  - Rejected: Report both the runner state and the refusal - the runner state is irrelevant to a run that will not happen, and a second line dilutes the one that matters
- **The mutating scenarios must not depend on whether the target drains its own queue**: The first real run of the operation-control scenario failed, and the diagnosis was worth more than the fix. src/api/app.py starts an embedded queue worker when worker_enabled is set, so a plain uvicorn target processes its own operations - and neither /health nor `capabilities` reports whether it does. A submitted operation therefore reaches a terminal state on its own on one target and sits queued indefinitely on another, from an identical sequence of steps, and the gate cannot classify the difference the way it classifies the runner and the target. Every step is now written to hold under both, and verified that way: the whole mutating suite passes against a local backend with the worker enabled and again with it disabled. The cost is named rather than hidden - `cancel` asserts only that it returned a parseable document, because its exit code is 0 from a queued operation and 1 from an already-failed one, and `retry`'s success path is uncovered because retry requeues from `failed` only.

  - Rejected: Design for an idle queue - the assumption the first version made, and it failed on the first run against an ordinary dev backend

  - Rejected: Assert a loose expectation that both outcomes satisfy - `expect` has no one-of for exit codes, and inventing one by dropping the assertion entirely would have been the same thing without the comment explaining it

  - Rejected: Rely on the Phase 4 report check alone - correct verdict, arrives after the submissions it should have prevented
  - Rejected: Batch the mutating scenarios so a combined run fits - buys one slot at the cost of masking (a failing operation type would hide the rest of its batch), to enable a run that is not a supported mode
  - Rejected: Lower the mutating scenarios' priority so they land in the remainder tier - they are the most important scenarios in the suite; putting them where truncation reaches first inverts the whole tier design
- **`{{ name }}` is two mechanisms sharing one delimiter, and which applies depends on another field**: The suite accounting rejected the operation-control scenarios outright, reporting `references undeclared parameter 'operation_id'`. It was half right. The pinned generator renders a template through Jinja2 with StrictUndefined only when it declares a `parameters` block; without one, `_expand_parameters` returns the template untouched and the braces survive to the evaluator, which interpolates them at runtime from values earlier steps captured. So the same syntax means a generation-time parameter or a run-time capture reference, and the two are mutually exclusive - a parameterized template cannot capture, because generation consumes the braces before the evaluator sees them. The accounting now checks both readings plus capture ordering, which is what lets any scenario chain steps at all.
  - Rejected: Use the CLI client's `[REDACTED:env_var]` substitution instead, which Jinja2 ignores - works only inside `args`, so assertions could not reference captured values, and it would encode a workaround for a rule we had misread
  - Rejected: Relax the accounting to ignore every `{{ }}` it cannot resolve - restores the silent drop the check was written to prevent
  - Rejected: Give the mutating scenarios a parameters block so the existing rule applies - would have destroyed the capture references at generation time and dropped every expansion with a log warning
- **Pinning the runner's ref pinned one node of a graph; the gate now owns the whole closure in a lock it does not share with the application**: D2 acquired the runner with `uvx --from 'gen-eval @ git+...@<sha>'`, and for six phases that read as fully pinned - the ref is immutable and the vendored schemas were generated from it. It is not. `uvx` resolves the transitive dependencies fresh on every invocation, so the enforcing gate was reproducible in the runner and floating in everything the runner imports. Replaced with a repository-owned uv project at `evaluation/runner/` whose direct requirement is still the immutable SHA and whose complete runtime and build closure is checked in as `evaluation/runner/uv.lock`; the gate invokes it as `uv run --project ... --locked --exact --no-dev --no-python-downloads`, so lock drift is fatal rather than silently resolved. `package = false` and a separate project directory keep it a tool rather than an application dependency - the root pyproject.toml and uv.lock are untouched and the runner's transitive dependencies cannot collide with this project's.
  - Rejected: Keep uvx and accept floating transitive dependencies - the gate's whole claim is that its verdict is a property of the repository, and a verdict that changes when an unrelated upstream releases is not that
  - Rejected: Add the runner to the root pyproject as a dev dependency - pins the closure but merges it with the application's, so a gen-eval transitive bound could constrain what the product itself can install
  - Rejected: Vendor the runner source into the repository - pins everything and destroys the upstream relationship the contract split was designed around; the pin would stop being a pin and become a fork
- **Once UP-1 through UP-4 landed, 'verified by construction' had to be deleted rather than kept as a fallback**: While `--print-contract-version` did not exist upstream, a pinned candidate was trusted by construction: it was installed from the exact ref the schemas were generated from, so the version was true by definition. The published console script now answers the probe, and the tempting move was to keep the construction argument as a fallback for when the probe fails. That is exactly backwards. If a pinned runner cannot complete the handshake, the thing that failed is the assumption the construction argument rests on, so the fallback would fire precisely when it is least entitled to. A pinned candidate that fails the probe is now MISMATCH - broken - and the failure detail carries the probe's exit code and last output line instead of an empty string.
  - Rejected: Keep construction as a fallback for probe failure - converts the one signal that the pin is not what it claims into a reason to trust it
  - Rejected: Treat a failed probe on a pinned runner as `unverifiable` like an arbitrary override - unverifiable is tolerated locally, and a broken pin should not be tolerated anywhere
- **Retaining evidence is publishing it, so the retained report is a minimized document that is re-validated after minimization**: A gen-eval report embeds what the CLI actually printed while talking to the target - stdout, stderr, and captured values from a real backend. Uploading that as a build artifact makes every one of those observations downloadable by anyone with access to the run, and the staging job runs against a deployed target with an admin key. `scripts/minimize_gen_eval_report.py` now writes a report without raw target observations and validates the *minimized* document against the report schema, not just the original: a redaction that produced a schema-invalid document would otherwise be discovered by whoever tried to consume the evidence. Both CI jobs upload only the minimized copy, and retention is conditional on that validation succeeding.
  - Rejected: Upload the raw report and rely on repository access control - makes the blast radius of an access mistake the whole observation set, for a convenience nobody asked for
  - Rejected: Skip retention entirely - the report is the only durable answer to 'what did the CLI actually do on that run', which is the question this roadmap item exists to make answerable
  - Rejected: Minimize without re-validating - the minimizer is code, and code that silently produces an unparseable artifact is worse than no artifact
- **The two CI jobs differ in trigger, target, and credential, so they are two jobs rather than one job with a matrix**: `read-only` runs on every pull request against an ephemeral localhost backend it boots itself - Postgres service container, migrations, uvicorn with `WORKER_ENABLED=false` - and needs no secret beyond test values. `staging-mutation` runs only on `workflow_dispatch` from `main`, against the protected `release-smoke-staging` GitHub environment, and is the only job that sees a real `ADMIN_API_KEY`. The target policy is materialized in-job with `jq` from that environment's `vars`, so no policy naming a real origin is ever committed and the deny registries come from the same environment that gates the credential. A matrix would have made the mutating job's approval gate an expression rather than a structural property.
  - Rejected: One job with a matrix over categories - the mutating leg's protection is the environment binding, and a matrix leg cannot be bound to a different environment than its siblings
  - Rejected: Run mutations on pull requests against the ephemeral backend - the policy model requires HTTPS for every non-local class, so there is no localhost path, and inventing one would mean a second opinion about the safe set
  - Rejected: Commit a staging policy file - puts a real origin and its deny registries in the repository, where they drift silently and are readable by anyone
- **Report credibility is validated at threshold zero so a failing run still leaves evidence, without letting that validation pass the gate**: The retention step re-runs the report validator with `--fail-threshold 0`. That still checks schema, expectation completeness, numeric bounds, and grouping - everything that makes a report worth keeping - while declining to re-assert the 95% pass rate. The run step already asserted that, under `continue-on-error: true`, and a final enforcement step requires both outcomes. The result is that the most useful artifact, the report from a failing run, is the one that survives; folding the threshold back into the retention step would have thrown that away exactly when it was needed.
  - Rejected: Validate at the real threshold in the retention step - drops the evidence for every failing run, which is every run anyone actually needs it for
  - Rejected: Retain unconditionally without validating - keeps unparseable or incomplete reports and makes the artifact's presence meaningless as a signal
  - Rejected: Let the retention step's success stand in for the gate - a credible report of a failing suite would then turn the job green

## Blockers
- Pinned-artifact distribution promotes the broken gen-eval console script from a routable-around defect to a real prerequisite. Under a sibling checkout, python -m gen_eval works; under a tool install the console script IS the published interface, and the installed executable fails with TypeError: main() missing 1 required positional argument: 'args'. Separately, the descriptor and Scenario pydantic models emit JSON Schema cleanly (8/9 and 12/6 props/defs) but GenEvalReport is a plain dataclass and cannot self-emit. → Filed as UPSTREAM.md in the change directory: UP-1 fixes the entry point (sync main() wrapping asyncio.run), UP-2 publishes the three schemas plus a contract version, preferably by promoting GenEvalReport to pydantic. Both are small agentic-coding-tools changes. ri-06 lands with vendored schemas and a documented interim entry-point form, then simplifies - task 7.3 retires the interim form once UP-1 ships.
- The pinned runner silently evaluates less than the suite it is given, by four independent mechanisms: an inert --categories flag, an unsettable scenario cap whose tier split reserves 40% for change detection that never reflows, and three logger.warning-and-continue paths for unparseable YAML, Jinja2 render errors, and model-validation failures. All exit 0. → Not blocking - worked around in-repo at a stated cost, and filed as UPSTREAM.md UP-6 with four sub-items, reproductions, and suggested fixes. The workaround cost real reporting granularity: batching means a failing command masks up to 3 others. Landing UP-6a/6b lets group-help.yaml go back to one scenario per command.

## Deviations
- Plan: Thin runner resolving gen-eval from ../agentic-coding-tools/packages/gen-eval, with an advisory skip when the sibling checkout is absent, on the grounds that this avoided creating a dependency. → Actual: Two-layer design: repository-local contract with vendored pinned schemas, plus a runner acquired as a pinned versioned artifact via uv tool. Sibling resolution survives only as developer convenience and is never used under enforcement. (reason: The operator rejected the original on the grounds that it still is a dependency and cannot be satisfied in cloud harnesses, sandboxes, VMs, or containers. The critique is correct: avoiding a [tool.uv.sources] entry removes only the resolver-visible dependency, converting a declared, versioned dependency into an undeclared, unversioned filesystem adjacency - not pinnable, not reproducible, invisible to tooling. The advisory-skip mode was the tell: an escape hatch invented because the dependency is not reliably satisfiable, which is exactly the mechanism behind agentic-assistant's silently-green gate. Generalizable lesson: if a design needs a skip mode to tolerate a missing dependency, the dependency is unsolved, not managed.)
- Plan: Phase 3 authors a descriptor and three read-only scenario categories (tasks 3.1-3.5); the runner filters by category and runs what it is given. → Actual: Two prerequisites had to be built first, added as tasks 3.6 and 3.7: gate-side target resolution (src/cli_gen_eval/target.py) and gate-side scenario selection (src/cli_gen_eval/selection.py). The help sweep was also restructured from 31 one-command scenarios into 8 batches of up to 4, and the contract validator now publishes scenarios_expected so Phase 4 can compare it against the report. (reason: Both prerequisites were assumptions about runner behaviour that turned out to be false, and both were caught by measuring rather than reading. The first suite run reported total_scenarios: 21 against an expected 39 with pass_rate 1.0 and exit 0; --categories was then found to be a no-op. Authoring the scenarios without these would have produced a suite that passed while covering roughly half of what it claimed, and that would eventually have submitted durable work by default.)
- Plan: Phase 4 implements scripts/validate_gen_eval_report.py with schema validation, minimum total and per-category counts, an empty unevaluated_interfaces, then the threshold; the gen-eval Make target runs contract, gate, then report validation. → Actual: The rules live in src/cli_gen_eval/report.py and run inside the gate on every invocation; the script is the standalone path for re-checking a retained artifact. The empty-unevaluated rule was replaced by a selection-scoped one, and the minimum count by set equality against a recorded expectation. Two tasks were added: 4.6 (record the request before the run, and separate the exit codes) and 4.7 (hold each scenario's declared interfaces to its steps). (reason: Three separate reasons, all discovered by measuring. The emptiness rule was measurably wrong - it rejects every category-scoped run. Report validation belongs inside the gate because Phase 6 calls run-gate.sh directly, so a third Make step would have been skippable by the exact caller that must not skip it. And the completeness comparison needs an artifact written before the run, which nothing in the plan produced.)
- Plan: Phase 5 implements the guard by consuming release-smoke's target policy, authors the workflow-submission and operation-control categories, and adds a test that the default selection excludes mutating categories. → Actual: All five planned tasks landed as written. Four more were added: 5.6 binds the policy to the origin the CLI resolves; 5.7 makes the scenarios independent of whether the target drains its own queue; 5.8 teaches the suite accounting the two meanings of {{ name }}; 5.9 refuses an over-capacity selection before the run. A sixth exit code was introduced for a refused mutation. (reason: Three of the four were forced by measurement rather than design review. The queue dependency was found by running the scenarios, not by reading them. The {{ }} collision was found by the accounting check rejecting valid scenarios. The origin binding was the one reasoned in advance, and it is the check that turns the policy from documentation into a control.)
- Plan: Phase 6 wires the read-only and mutating gates into CI and Phase 7 documents the suite; the runner is acquired as a pinned artifact via `uvx --from` at an immutable git ref (D2). → Actual: Both phases landed as planned. A subsequent review pass then replaced the acquisition mechanism with a repository-owned locked uv project, deleted the 'verified by construction' version path in favour of the now-published handshake, and introduced report minimization before any artifact is retained. (reason: The review asked what the gate trusts that it has not verified. Three answers: the runner's transitive dependency graph was resolved fresh on every invocation, a pinned runner's contract version was asserted rather than asked now that asking is possible, and the retained artifact carried raw observations from a credentialed staging target. None were reachable by testing the gate's behaviour - each is a property of what the gate takes on faith, which only a boundary-shaped question surfaces.)

## Recommendations
- Execute UPSTREAM.md UP-1 and UP-2 in agentic-coding-tools first; they are small and unblock the clean form of D1 and D4.
- Implementation starts at Phase 1 (contract layer) - it is the only phase with no external dependency and it must be independently green before Phase 2.
- Add an installed-artifact test upstream (build wheel, install into a throwaway venv, run the console script). The existing suite only exercises the module path, which is why the broken entry point survived.
- Also file the agentic-assistant gate defect: its probe is the broken console script and it passes a --scenario flag gen-eval does not accept, so it has never evaluated anything.
- ri-07, ri-10, and ri-11 depend on ri-06; ri-11 expects executable compatibility evidence from this suite, so Phase 6's retained report artifact is its input.
- When adopting an external evaluation runner, measure what a run actually evaluated before trusting its pass rate. Three of Phase 3's four significant findings came from comparing report totals against an independently computed expectation; none would have surfaced from reading the runner's --help, and one (--categories) is documented as working.
- Phase 4's report validator must compare total_scenarios against the contract validator's scenarios_expected, and must compute coverage against the SELECTED interfaces rather than every descriptor-declared one - a single-category run legitimately leaves 28 of 31 interfaces unevaluated, so the planned 'unevaluated must be empty' rule would fail every partial run.
- Phase 5 must not rely on category selection alone to hold mutating scenarios back. Gate-side selection now enforces it, but the target-policy guard should refuse independently, so two mechanisms have to fail before durable work is submitted.
- Interface coverage in this runner is 'attempted', not 'passed' - interfaces_tested is derived from a scenario's declared steps regardless of which ones ran. Coverage percent and pass rate answer different questions, and only the second means the surface works.
- A pass rate is a statement about what ran, never about what was asked for. Any gate over an external runner needs an independently computed expectation recorded before the run, or its green means 'whatever happened, happened successfully'.
- When a planned rule turns out to be wrong, measure before rewriting it. The emptiness rule looked right on paper and failed the first partial run; what fixed it was running --categories validation --offline and reading the 29 unevaluated interfaces, not reasoning about the runner's source.
- Phase 5's mutating scenarios inherit all of this for free - a workflow-submission scenario that never ran, or one that ran outside its selection, is now a named exit-5 failure. The target-policy guard should still refuse independently, so two mechanisms must fail before durable work is submitted.
- Phase 6 must treat exit 5 as a distinct CI outcome, not fold it into failure. A credibility failure means the evidence is unusable, which is a different remedy from a red test - and if CI collapses them, the distinction the code maintains stops reaching anyone.
- Metadata a tool ignores will be wrong. The scenarios' `interfaces:` field is inert to the runner, and two of sixteen scenarios had it wrong the moment anything checked - including the one carrying the ri-01 proof, which credited no interface at all.
- Author scenarios against a real target before believing them. Ten mutating scenarios were written from the source of the CLI and the API and looked right; the first run failed one of them for a reason no amount of reading would have surfaced, because the cause was an embedded worker in the API process.
- When a prerequisite cannot be classified, do not tag it - design around it. The queue-drain state is invisible from the target, so a `requires-idle-queue` tag would have been an unverifiable precondition presented as a verified one, which is the failure mode this whole roadmap item exists to remove.
- A safety check earns its own exit code. Exit 6 separates 'something asked to write where it was not allowed' from 'the invocation was malformed'. Phase 6 must not fold 4, 5, and 6 into a single red - they are three different remedies, and CI is where the distinction either reaches a human or dies.
- Two mechanisms, not one, for anything irreversible. Selection filters files and says nothing about where they point; the guard describes a target and says nothing about what is on disk. Either alone is a single point of failure, and the tests assert both independently.
- Phase 6's mutating job needs a deployed staging or ephemeral target - the policy model requires HTTPS for every non-local class, so there is no localhost path. The read-only job has no such constraint and should stay on the cold-start template. Verifying a change to the mutating scenarios locally means invoking the pinned runner directly against a materialized selection, outside the gate.
- Pinning a dependency's version is not pinning a dependency. `uvx --from 'pkg @ git+...@<sha>'` fixes one node and floats the rest of the graph; only a checked-in lock invoked with `--locked --exact` makes an enforcing gate's verdict a property of the repository.
- When an upstream capability you worked around finally lands, delete the workaround instead of demoting it to a fallback. A fallback for 'the handshake failed' fires exactly when its own premise is false.
- Ask what a change trusts without verifying, separately from asking whether it works. Every finding in the review pass was a trust boundary - dependency closure, version assertion, artifact contents - and the full suite was green before and after each one.
- Treat CI artifact retention as publication. A gen-eval report embeds real target output; the staging job's target holds a real admin key. Minimize first, re-validate the minimized document, and make retention conditional on that validation.
