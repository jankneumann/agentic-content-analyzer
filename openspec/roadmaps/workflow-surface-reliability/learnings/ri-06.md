- title: Completeness is a fact about the request, so the request is recorded before

  outcome: 'A report cannot establish its own completeness - nothing inside it says

  - Trust the runner's own exit code - it is computed from the reduced set, so it

- title: Coverage is checked against the selection, not the descriptor; the planned
    rule was wrong
  outcome: 'D7 named the rule ''fail when any descriptor-declared interface is unevaluated''.
    Measuring it showed it would reject every partial run: the runner computes coverage_pct
    against descriptor.all_interfaces(), so `--categories validation --offline` evaluates
    2 scenarios, passes 100%, and reports 29 of 31 interfaces unevaluated - correctly.
    The check is now scoped to the interfaces the selection addresses. Two further
    checks fill the gap that scoping opens: every interface in per_interface must
    be descriptor-declared or in a reviewed exception set (a mistyped step command
    credits a phantom interface and leaves the real one uncovered, with no runner
    error), and each scenario''s declared `interfaces` must match what its steps will
    credit. Coverage is read from the report''s own fields rather than recomputed
    (D7''s other half), because a second implementation of the runner''s aggregation
    would disagree with it in ways indistinguishable from the defect it is meant to
    find.'
  alternatives_rejected:
  - Keep the emptiness rule and only ever run the full suite - gives up category-scoped
    runs, which is what CI needs for a fast PR job
  - Drop the coverage check entirely and rely on the scenario-count check - misses
    the typo case, where the count is right and the coverage is not
  - Widen the descriptor per run so its denominator equals the selection - changes
    the coverage denominator itself, so a genuinely uncovered command would stop being
    visible as one
- title: '''The suite failed'' and ''the report is not credible'' get different exit
    codes'
  outcome: 'Exit 1 stays ''a scenario failed'', which is a defect in aca. Exit 5 is
    new: the run finished but its report cannot decide the question - scenarios dropped,
    coverage missing, counts that contradict each other, numbers out of range. The
    two land on different desks, and collapsing them would hide the second behind
    the first, which is precisely the failure mode this roadmap item exists to remove.
    The same split runs through the code: Finding carries a severity, ReportVerdict.credible
    is separate from .ok, and validation runs on every gate invocation whether or
    not the runner exited zero - the interesting case is exactly the one where it
    reported success over work it silently dropped.'
  alternatives_rejected:
  - Report an incredible run as a suite failure (exit 1) - the reader concludes aca
    is broken and goes looking for a product bug that does not exist
  - Report it as a usage error (exit 2) - nothing about the invocation was wrong
  - Let the runner's --fail-threshold be the only gate - it computes the rate from
    whatever survived truncation, so 100% of a third of the suite passes it
- title: Fixtures are recorded runner output; the negative cases are mutations in

The same split runs through the code: Finding carries a severity, ReportVerdict.credible is separate from .ok, and validation runs on every gate invocation whether or not the runner exited zero - the interesting case is exactly the one where it reported success over work it silently dropped.
  - Rejected: Report an incredible run as a suite failure (exit 1) - the reader concludes aca is broken and goes looking for a product bug that does not exist
  - Rejected: Report it as a usage error (exit 2) - nothing about the invocation was wrong
  - Rejected: Let the runner's --fail-threshold be the only gate - it computes the rate from whatever survived truncation, so 100% of a third of the suite passes it
- **Fixtures are recorded runner output; the negative cases are mutations in the test**: tests/fixtures/gen_eval/ holds two real runs - full and --offline - each paired with the expectation the gate wrote for it. Only edit is truncating captured stdout bodies over 120 chars, which removed about 120 KB of --help screens; a test asserts the fixtures are still schema-valid so the truncation cannot have corrupted them quietly. No malformed report is checked in: each is derived in the test by mutating a loaded fixture, so the mutation sits beside the assertion it trips and cannot drift from the fixture it came from. The validator itself was then mutation-tested - disabling each check fails only the tests naming it, including reverting the scoped-coverage rule to the naive emptiness rule, which fails exactly the test documenting why it is wrong.
  - Rejected: Hand-author the reports - a fixture that restates what we believe the runner emits proves the validator agrees with our belief, not with the runner
  - Rejected: Check in a report-truncated.json - it would assert that scenarios went missing; `report['verdicts'][:8]` in the test demonstrates it
  - Rejected: Keep the reports byte-complete at 167 KB - the trimmed content is help text no check reads, and it dominated the artifact

## Blockers
- Pinned-artifact distribution promotes the broken gen-eval console script from a routable-around defect to a real prerequisite. Under a sibling checkout, python -m gen_eval works; under a tool install the console script IS the published interface, and the installed executable fails with TypeError: main() missing 1 required positional argument: 'args'. Separately, the descriptor and Scenario pydantic models emit JSON Schema cleanly (8/9 and 12/6 props/defs) but GenEvalReport is a plain dataclass and cannot self-emit. → Filed as UPSTREAM.md in the change directory: UP-1 fixes the entry point (sync main() wrapping asyncio.run), UP-2 publishes the three schemas plus a contract version, preferably by promoting GenEvalReport to pydantic. Both are small agentic-coding-tools changes. ri-06 lands with vendored schemas and a documented interim entry-point form, then simplifies - task 7.3 retires the interim form once UP-1 ships.
- The pinned runner silently evaluates less than the suite it is given, by four independent mechanisms: an inert --categories flag, an unsettable scenario cap whose tier split reserves 40% for change detection that never reflows, and three logger.warning-and-continue paths for unparseable YAML, Jinja2 render errors, and model-validation failures. All exit 0. → Not blocking - worked around in-repo at a stated cost, and filed as UPSTREAM.md UP-6 with four sub-items, reproductions, and suggested fixes. The workaround cost real reporting granularity: batching means a failing command masks up to 3 others. Landing UP-6a/6b lets group-help.yaml go back to one scenario per command.

## Deviations
- Plan: Thin runner resolving gen-eval from ../agentic-coding-tools/packages/gen-eval, with an advisory skip when the sibling checkout is absent, on the grounds that this avoided creating a dependency. → Actual: Two-layer design: repository-local contract with vendored pinned schemas, plus a runner acquired as a pinned versioned artifact via uv tool. Sibling resolution survives only as developer convenience and is never used under enforcement. (reason: The operator rejected the original on the grounds that it still is a dependency and cannot be satisfied in cloud harnesses, sandboxes, VMs, or containers. The critique is correct: avoiding a [tool.uv.sources] entry removes only the resolver-visible dependency, converting a declared, versioned dependency into an undeclared, unversioned filesystem adjacency - not pinnable, not reproducible, invisible to tooling. The advisory-skip mode was the tell: an escape hatch invented because the dependency is not reliably satisfiable, which is exactly the mechanism behind agentic-assistant's silently-green gate. Generalizable lesson: if a design needs a skip mode to tolerate a missing dependency, the dependency is unsolved, not managed.)
- Plan: Phase 3 authors a descriptor and three read-only scenario categories (tasks 3.1-3.5); the runner filters by category and runs what it is given. → Actual: Two prerequisites had to be built first, added as tasks 3.6 and 3.7: gate-side target resolution (src/cli_gen_eval/target.py) and gate-side scenario selection (src/cli_gen_eval/selection.py). The help sweep was also restructured from 31 one-command scenarios into 8 batches of up to 4, and the contract validator now publishes scenarios_expected so Phase 4 can compare it against the report. (reason: Both prerequisites were assumptions about runner behaviour that turned out to be false, and both were caught by measuring rather than reading. The first suite run reported total_scenarios: 21 against an expected 39 with pass_rate 1.0 and exit 0; --categories was then found to be a no-op. Authoring the scenarios without these would have produced a suite that passed while covering roughly half of what it claimed, and that would eventually have submitted durable work by default.)
- Plan: Phase 4 implements scripts/validate_gen_eval_report.py with schema validation, minimum total and per-category counts, an empty unevaluated_interfaces, then the threshold; the gen-eval Make target runs contract, gate, then report validation. → Actual: The rules live in src/cli_gen_eval/report.py and run inside the gate on every invocation; the script is the standalone path for re-checking a retained artifact. The empty-unevaluated rule was replaced by a selection-scoped one, and the minimum count by set equality against a recorded expectation. Two tasks were added: 4.6 (record the request before the run, and separate the exit codes) and 4.7 (hold each scenario's declared interfaces to its steps). (reason: Three separate reasons, all discovered by measuring. The emptiness rule was measurably wrong - it rejects every category-scoped run. Report validation belongs inside the gate because Phase 6 calls run-gate.sh directly, so a third Make step would have been skippable by the exact caller that must not skip it. And the completeness comparison needs an artifact written before the run, which nothing in the plan produced.)

## Recommendations
- Execute UPSTREAM.md UP-1 and UP-2 in agentic-coding-tools first; they are small and unblock the clean form of D1 and D4.
- Implementation starts at Phase 1 (contract layer) - it is the only phase with no external dependency and it must be independently green before Phase 2.
- Add an installed-artifact test upstream (build wheel, install into a throwaway venv, run the console script). The existing suite only exercises the module path, which is why the broken entry point survived.
- Also file the agentic-assistant gate defect: its probe is the broken console script and it passes a --scenario flag gen-eval does not accept, so it has never evaluated anything.
- ri-07, ri-10, and ri-11 depend on ri-06; ri-11 expects executable compatibility evidence from this suite, so Phase 6's retained report artifact is its input.
- When adopting an external evaluation runner, measure what a run actually evaluated before trusting its pass rate. Three of Phase 3's four significant findings came from comparing report totals against an independently computed expectation; none would have surfaced from reading the runner's --help, and one (--categories) is documented as working.
- Phase 4's report validator must compare total_scenarios against the contract validator's scenarios_expected, and must compute coverage against the SELECTED interfaces rather than every descriptor-declared one - a single-category run legitimately leaves 28 of 31 interfaces unevaluated, so the planned 'unevaluated must be empty' rule would fail every partial run.
- Phase 5 must not rely on category selection alone to hold mutating scenarios back. Gate-side selection now enforces it, but the target-policy guard should refuse independently, so two mechanisms have to fail before durable work is submitted.
- Interface coverage in this runner is 'attempted', not 'passed' - interfaces_tested is derived from a scenario's declared steps regardless of which ones ran. Coverage percent and pass rate answer different questions, and only the second means the surface works.
- A pass rate is a statement about what ran, never about what was asked for. Any gate over an external runner needs an independently computed expectation recorded before the run, or its green means 'whatever happened, happened successfully'.
- When a planned rule turns out to be wrong, measure before rewriting it. The emptiness rule looked right on paper and failed the first partial run; what fixed it was running --categories validation --offline and reading the 29 unevaluated interfaces, not reasoning about the runner's source.
- Phase 5's mutating scenarios inherit all of this for free - a workflow-submission scenario that never ran, or one that ran outside its selection, is now a named exit-5 failure. The target-policy guard should still refuse independently, so two mechanisms must fail before durable work is submitted.
- Phase 6 must treat exit 5 as a distinct CI outcome, not fold it into failure. A credibility failure means the evidence is unusable, which is a different remedy from a red test - and if CI collapses them, the distinction the code maintains stops reaching anyone.
- Metadata a tool ignores will be wrong. The scenarios' `interfaces:` field is inert to the runner, and two of sixteen scenarios had it wrong the moment anything checked - including the one carrying the ri-01 proof, which credited no interface at all.
