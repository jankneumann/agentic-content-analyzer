### Decisions
1. **Host-side only; railway/postgres/** untouched** `architectural: backup-and-restore` — verify-production-paradedb-langfuse edits those files and treats the current backup as a cutover precondition; repointing it mid-flight would invalidate that change's rollback evidence. The dead-job finding is recorded in docs/GOTCHAS.md instead.
2. **RPO 24h via daily dumps; WAL archiving deferred** `architectural: backup-and-restore` — Ingested content is re-derivable from still-available external sources. Human-authored data (review decisions, prompt and source overrides) is the real exposure and is the trigger to revisit. A tested simple restore beats an untested complex one for RTO.
3. **Client-side age encryption before upload** `architectural: backup-and-restore` — Dumps contain subscriber emails, OAuth tokens and audit logs. SSE protects against disk theft but not against bucket-credential holders. Client-side encryption turns a credential leak into a denial-of-access problem.
4. **Freshness derives from a bucket-side manifest, not cron.job_run_details** `architectural: backup-and-restore` — The question that matters is whether an artifact arrived at the destination, not whether the source believes it ran. A manifest answers that, is provider-independent, and survives destruction of the source host.
5. **Widen the durable alert path rather than use in-app notifications** `architectural: observability` — The in-app path fails open, so a failed alert is indistinguishable from no problem — unacceptable for a durability signal. Widening WorkflowAlertEnvelopeV1 requires changing five elements together and making operation-scoped fields optional rather than synthesized.
6. **Retention via provider-side lifecycle rules; no unattended delete** `architectural: backup-and-restore` — Provider-side retention keeps working while gx-10 is down — exactly when a cleanup cron would stop, leaving retention silently unenforced. Also satisfies the no-unattended-deletion constraint structurally.

### Alternatives Considered
- Host shell script + systemd (Approach A): rejected because Shell resists unit testing, so destructive and credential-handling paths would ship unverified — the exact risk the gatekeeper flagged.
- Pure Python backup service (Approach B): rejected because Requires declaring boto3 and encryption bindings, and streams multi-GB dumps through the interpreter, re-implementing tools that already work correctly.
- Retire or repair the pg_cron job in this change: rejected because Head-on conflict with an in-flight change; repair is additionally blocked by the documented Railway restriction on app.* GUCs.
- Reuse FileSyncer for artifact backup: rejected because It discovers files via DB reference columns, so orphaned and mid-transaction files are invisible to it. Correct for sync, wrong for disaster recovery.

### Trade-offs
- Accepted Up to 24h of data loss over Near-zero RPO via WAL archiving because Most content is re-ingestable; a short tested runbook serves RTO better than a long untested one.
- Accepted A lost age identity key makes all backups unrecoverable over Provider-side encryption only because Mitigated by dual escrow, a canary decryption check in verify, and a runbook that leads with key recovery.
- Accepted Two backup mechanisms coexist temporarily over Retiring the dead one now because Avoids a merge conflict and forced sequencing with an in-flight change; the inert one is documented so the finding is not lost.
- Accepted Backup over-copies orphaned artifact files over DB-reference-driven file discovery because Over-inclusion is the safe error direction for a backup.

### Context
Planned the first working disaster-recovery backup scheme for the gx-10 self-hosted migration. Investigation established that the existing pg_cron backup has never produced a backup (MinIO endpoint never wired, job body self-skips, mc binary absent from the DB image), and that its health check is gated behind the railway provider so it cannot fire on gx-10. Selected a Python-orchestrated, native-tool-executing design across seven work packages with no scope or lock overlap.
